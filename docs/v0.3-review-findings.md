## A. Blocking — these change schema or arithmetic, and cost real work if found in code

### A1. `PHASE2_MAX_POINTS` is 50, not 35 — which makes `ADVANCE_THRESHOLD` 5 and the gate a no-op

D1 defines `PHASE2_MAX_POINTS` as "the sum of the maximum positive points from all rules whose inputs are Phase-2-only signals," computed from the live ruleset. It then asserts that value is 35: `qual.own_brand` + `opp.ai_invisible` + `opp.slow_site`.

**`qual.owner_operated` (+15) is also Phase-2-only.** All three of its disjuncts are:

| Disjunct | Source | Phase |
|---|---|---|
| `legal_form ∈ {e.K., Einzelunternehmen, GbR}` | `ImpressumExtract.legal_form` | 2 |
| ≤ 2 natural-person Geschäftsführer | `impressum.gf_count` | 2 |
| owner named on site | `HomepageExtract.owner_named_on_site` | 2 |

Nothing in §5.1 or §5.3 populates `company.legal_form` — Places returns `displayName`, `websiteUri`, `formattedAddress` only, and no deterministic parser reads legal form. So a correct derivation gives **50**, and `ADVANCE_THRESHOLD = 55 − 50 = 5`.

Two consequences:

1. **The startup assertion fires on day one.** D1 says to "fail loudly if the two disagree" — a correct implementation and the spec's own stated value disagree immediately.
2. **The gate stops gating.** At a threshold of 5, `qual.ecommerce_platform` alone (+15) admits a company. Essentially every shop advances to Phase 2, so §7's "55–70% advance" and the $20–35/month estimate are both wrong on the low side.

Needs a decision, not a patch. Options as I see them:

- **(a)** Accept that `qual.owner_operated` is Phase-2-only, take the threshold of 5, and restate §7's cost model at ~95% advance rate. Honest, and expensive.
- **(b)** Add a cheap deterministic Phase-1 proxy for legal form — the shop footer and the Impressum page's raw text both usually contain `GmbH` / `e.K.` / `UG` literally, and §5.2 already fetches the Impressum. A regex over the *fetched* Impressum HTML is free and Phase-1. That moves the +15 out of `PHASE2_MAX_POINTS` legitimately and restores the threshold to 20.
- **(c)** Exclude `qual.owner_operated` from the sum by fiat. This makes the assertion a lie and I would not do it.

**(b) looks right** — it costs one more deterministic parser in M2 and preserves both the gate and the cost model. But it is a scoring-adjacent change, and §"Stop and ask" in the brief says the spec owns rule predicates, so it is your call.

### A2. Phase-2 extraction outputs have no signal keys, and `qual.own_brand` has no data path

§5.5b defines two Pydantic models. Nothing maps their fields to `signal.key` values, to `contact` rows, or to `company_profile` columns.

The sharpest instance: **`qual.own_brand` (+10) is a live scoring rule and a term in `PHASE2_MAX_POINTS`, but `HomepageExtract.own_brand` has no signal key and no view column.** It cannot be scored as written. Same gap for `one_line_offer`, which §5.5c needs to derive queries and §9 displays as a table column.

Needed before M5: a table mapping each `ImpressumExtract` / `HomepageExtract` field to (signal key | contact column | discarded), plus the corresponding `company_profile` columns. Suggested keys, for you to accept or replace:

| Field | Key |
|---|---|
| `own_brand` | `brand.own_brand` (num 0/1) |
| `one_line_offer` | `offer.one_line` (text) |
| `product_categories` | `offer.categories` (text, pipe-separated) |
| `audience` | `offer.audience` (text) |
| `owner_named_on_site` | `impressum.owner_named` (num 0/1) — **already in the view** |
| `legal_form` | writes `company.legal_form` |
| `managing_directors` | `impressum.gf_count` (num) + `contact` rows |
| `agency_credit` | see A3 |

### A3. `agency.footer_credit` is written by two methods with no merge rule

D1 says `neg.has_agency` "may fire on `HomepageExtract.agency_credit` where the footer regex missed it." But the LLM value has no key of its own, and `company_profile` resolves `agency.footer_credit` to the **latest observation regardless of method**. If the LLM writes to the same key, then:

- an LLM `null` observed after a deterministic hit silently erases a real finding, and
- a −20 point swing depends on which of two writes landed second.

Needs either a separate key (`agency.llm_credit`) with an explicit OR in the rule, or a documented precedence rule in the view.

### A4. `company_profile` has no `confidence` column, so `confidence=0` values feed scoring

§5.5b: a value failing substring verification "is discarded and the signal written with `confidence=0` for review." §9: those fields render red because you must not trust them in a letter.

But scoring reads `company_profile`, which pivots the latest observation per key with no confidence filter. So a value the spec calls *discarded* is exactly what `qual.owner_operated` and `qual.own_brand` will score on. §5.5b and §4 contradict each other.

Fix is small but must be chosen: either the view excludes `confidence = 0` rows, or it exposes a parallel `*_confidence` column and every rule guards on it. The former is simpler and matches the stated intent of "discarded."

### A5. No product page is ever fetched, so `opp.no_product_schema` (+10) can never fire

v0.2's §5.2 fetch order stops at the blog index. `artifact.kind` includes `'product_page'` and §5.3 requires checking JSON-LD on "a sample product page," but nothing retrieves one.

**I made a minimal edit** to the merged §5.2 fetch order, appending "→ one sample product page if a product path is found," so the spec is at least self-consistent. **The selection rule is still undefined** and I did not invent one: which URL from `catalog.product_url_count` is the sample, and what happens when the product sitemap is the only source. Please specify — a stable rule (e.g. first URL in document order from the product sitemap) matters for reproducibility, since a randomly-chosen sample makes `schema.product_present` non-deterministic across runs.

## B. Contradictions and undefined behaviour

### B1. Brief export: "fail loudly" vs. "omit entirely"

The implementation brief's M7 gate is *"Export fails loudly when `ai.*` basis fields are missing."* §9 says *"Briefs for companies that did not reach Phase 2 omit the KI-Sichtbarkeit section entirely rather than rendering it empty."* Taken literally, every C/D-band brief fails.

The intended predicate is presumably: assert the `ai.*` fields **only when the KI-Sichtbarkeit section is rendered**, and render it only when the company reached Phase 2. Third case is unhandled: a Phase-2 company whose AI check errored — `ai.queries_checked = 0`, no `ai.query_text`. Omit, or fail?

### B2. `needs_review_reason` is one column; three flags can co-occur

`no_impressum`, `possible_marketplace_only`, and D2's new `blog_date_unparseable` are independent and can all apply to one company. The schema stores one `TEXT`. Either the column becomes a delimited list with a documented separator, or review reasons move to their own table. (I added `blog_date_unparseable` to §6.4's soft-flag list — D2 introduces the value but never registers it there.)

### B3. Batch reconciliation across run boundaries has no cost-ledger rule

Three unspecified points, all in the same area:

1. `portal reconcile` runs under a **new** `run_id`, but the batch's `est_cost_usd` was reserved against the *submitting* run. When `actual_cost_usd` is written, does the submitting run's `est_cost_usd` get corrected — mutating a closed run's ledger — or does the delta land on the reconciling run?
2. The 30-day ceiling (§7.2) sums `run.est_cost_usd`, which is **estimates only, never actuals**. If estimates are conservative-high by design (§7.3 says the failure mode should be over-counting), the rolling ceiling bites systematically early. That may be acceptable, but it should be stated rather than discovered.
3. **`reconcile` must be exempt from the ceiling check.** Polling a batch is free, and the spend is already committed. If a ceiling breach blocks `reconcile`, you have paid for results you can never write to the database. This is a one-line rule but a real trap.

### B4. `run_id` for reconciled signals is undefined

Related to B3 but distinct: signals written by `reconcile` need a `run_id` (NOT NULL, FK). The submitting run's — which makes `uq_signal_identity` behave as intended but writes into a finished run — or the reconciling run's? Pick one and write it down; it determines whether re-running `reconcile` after a partial failure deduplicates.

### B5. Ruleset version is inconsistent across the source documents

The delta header says "No new features. Scoring weights unchanged except where noted," but D1 refers to "ruleset v3" while v0.2's §6 heading says "ruleset v2." Both are defensible — predicates changed even though weights didn't, which justifies a bump. **I set the §6 heading to v3** to match D1. Confirm, and note that `score.ruleset_version` is a stored string whose canonical value is never defined anywhere; M3 needs it as a named constant.

### B6. `PHASE2_MAX_POINTS` implies a ruleset representation the spec never defines

D1's startup assertion requires deriving the sum from "the live ruleset" — which means rules must exist as data carrying, per rule, their input signal keys and a phase tag. The spec describes rules only as prose tables. This is an M3 structural requirement hidden inside a defect fix; worth making explicit before M3 rather than discovering it while writing the scorer.

### B7. `qual.own_domain_shop` (+5) has no predicate anywhere

Presumably the negation of §6.4's `possible_marketplace_only` (≥ 5 product URLs on own domain), but that is inference. Define it or drop it.

## C. Judgment calls worth confirming — not defects

### C1. The blog ladder scores a healthy new blog as an opportunity

Chain order is `stale(>365)` → `thin(<10)` → `slowing(≥180)`. So a shop that started blogging three months ago and has published 8 posts hits `opp.thin_blog` **+12** — it is checked before any recency rung. A shop with 20 posts and nothing for 200 days gets `opp.blog_slowing` **+10**, i.e. *less*.

If "thin" is meant as "they tried and gave up," the count check should come after the recency rungs. If it is meant as "there isn't much there to work with," current order is right. D2 fixed the overlap; it did not settle the intent. Worth deciding before M3, because it is invisible once the chain is code.

### C2. One failed search silently costs `opp.ai_invisible` its +15

`opp.ai_invisible` requires `ai.queries_checked >= 2`, and D4 sets the default to exactly 2. Any single search that errors — `too_many_requests` is an explicit error code — drops `queries_checked` to 1 and the rule cannot fire. The company reads as "not AI-invisible" when in fact it was not measured. No retry or partial-result policy is specified. Suggest either retrying failed searches within the stage, or recording `ai.check_incomplete` and routing to `needs_review` rather than scoring 0.

### C3. M7 depends transitively on the blocked M6

The build order has M6 (AI-visibility) explicitly blocked pending the D4 pricing confirmation, and M7 (brief export) after it. Since M7's export asserts on `ai.*` fields, M7 is blocked too unless B1's predicate is resolved so briefs render without a KI-Sichtbarkeit section. Resolving B1 unblocks M7 independently of M6 — worth doing, since the brief export is useful on Phase-1 data alone.

### C4. `uq_signal_identity` includes `evidence_url`, so a redirect defeats dedup

If a re-fetch lands on `example.de/impressum/` where the previous run saw `example.de/impressum`, the unique index treats the observation as new. Harmless given append-only semantics, but it means "no duplicate observations within a run" is slightly weaker than it reads.

## D. D4's open question — resolved

D4 said: *"Before implementing, confirm the web search tool's billing rate… Do not ship this sub-stage with an unverified cost."*

**Confirmed against the current Anthropic API pricing documentation, 2026-08-15:**

| Item | Value |
|---|---|
| Web search | **$10 per 1,000 searches** ($0.01/search), charged **in addition to** token costs |
| Billing unit | One search = one use regardless of result count; **errored searches are not billed** |
| Reporting | `usage.server_tool_use.web_search_requests` per response |
| Batch API | Does **not** discount the per-search charge — batch web-search calls are priced the same as regular ones |
| Haiku 4.5 tokens | $1/MTok input, $5/MTok output (batch: $0.50 / $2.50) |

At the D4 default of 2 queries per company: **$0.02/company in search fees**, on top of ~$0.03–0.04 in tokens → **$0.05–0.06 per company** for the AI-visibility sub-stage. I have written this into §5.5c and §7.8 of the merged spec, with the reservation rule stated as `$0.01 × planned_queries`.

Two follow-ons this surfaced:

- **D4's 10–20k token estimate holds, and for a specific reason.** Dynamic filtering — where search results are filtered by code *before* entering the context window — requires Claude 4.6 or later. Haiku 4.5 predates it, so the model must use the basic `web_search_20250305` tool with `allowed_callers: ["direct"]`, and every search result lands in context in full. The high estimate is the correct one for this model choice.
- **Still to verify before M6:** that Claude Haiku 4.5 supports the web search tool at all. The pricing and tool-reference pages both defer model-compatibility to the other, and I could not confirm it from either. If Haiku 4.5 is not supported, §5.5c's model choice changes and the token cost with it — a Sonnet-tier model would be ~2–3× the token cost per query. This is a five-minute check against a live API call and should happen before M6 is scheduled, not during it.
